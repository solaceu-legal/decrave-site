# Decrave：增长报告审查与分期优化计划

日期：2026-10-03（北京时间）

本轮优先级：官网下载转化优先，同时推进自然搜索曝光。

状态：审查与计划已完成；第 1、2 期已实施并于 2026-10-03 22:04 发布官网，统计后台配置已更新；App 未修改。详见 [实施记录](Decrave-第1-2期实施记录.md)。

## 1. 结论与证据边界

这份报告适合作为增长假设清单，不能作为科学研究、完整技术审计或已验证的增长结论。它没有给出调研时间、原始数据、用户样本、竞品逐项比较、性能测试和收益估算，且遗漏了官网现有的多项能力。

我们应该保留其关于降低入门压力、建立真实信任和提供下载前体验的方向；按“现状核实 → 小改动 → 验收 → 观察”的方式执行。优先让已有能力发挥作用。

本轮证据：

- 实际读取公开首页、`guides/index.html`、隐私政策，三个页面的内容与本地对应文件逐字一致。
- 本地首页、样式、8 篇指南、部署流程、App 语言配置、Analytics 和 CloudKit 初始化代码。
- `docs/website-analytics-setup.md`、`docs/seo-next-phase.md`、版本与商店文案记录。
- WHO、Cochrane、Google Search Central、web.dev、Apple 和 Android 的公开资料。

审查阶段尚未核实：最新 Plausible/GSC/Bing/ASC 后台数据、线上商店评分与新版截图、现场 Core Web Vitals、当前订阅与试用配置、真实用户反馈。本地配置和历史记录不能替代当前后台验证。后续实施已读取 Plausible 与 GSC 基线并完成本地性能诊断；其余仍以实施记录中的未完成项为准。

## 2. 对报告的逐项判断

### 用户体验、定位和差异化

| 报告判断 | 审查结果 | 我们的行动 |
| --- | --- | --- |
| 信息层级清楚、三步引导和对比易理解 | 是设计判断；代码能确认结构，但“易理解”需要用户验证 | 保留主体结构，找 5 位目标用户做方向性的理解测试 |
| “不设戒烟日期”有共鸣 | 合理的定位假设；应表述为“不必先设戒烟日期”，App 仍支持以后选择日期 | 保留核心标题，检查用户是否误解为永远不需要完全停止吸烟 |
| 目标群体是吸烟者的大多数、最大的未开发群体 | 未给出地区、时间、阶段定义和抽样来源；意愿也不等于付费需求 | 从目标市场访谈和真实使用建立需求依据，不把百分比写进营销 |
| 这是蓝海、所有竞品都围绕戒烟日期 | 缺少竞品版本及功能核查 | 把差异化限定在 Decrave 的具体体验，减少笼统贬低竞品 |
| 不清零解决首要弃用原因 | 有行为设计上的合理性，但未证明排名、因果或产品效果 | 不宣称提高戒烟成功率；后续用用户访谈与使用反馈验证 |
| 同伴支持是病毒传播关键，所以要推荐计划 | 社会支持、主动分享和获客传播是三个不同问题 | 先观察自然推荐需求，再考虑轻量分享；不先做奖励系统 |

“无需先设戒烟日期”是开始使用的条件，不能推导出一种更有效的戒烟方法。Cochrane 的综述认为“逐步减少后戒烟”与“一次性停止”的长期戒烟率可能相近；研究对象是以最终戒烟为目标的干预，证据截至 2018 年，不能套用为无限期减量或 Decrave 的效果证据。[Cochrane 综述](https://www.cochrane.org/evidence/CD013183_can-people-stop-smoking-cutting-down-amount-they-smoke-first)

WHO 2024 指南允许数字工具作为自我管理或辅助支持；这并不证明任意一款 App 有效，也不支持替代有证据的其他支持。练习完成、计数增长、留存和戒烟成功是不同指标。[WHO 指南建议](https://www.ncbi.nlm.nih.gov/books/NBK604665/)

### 营销、信任与转化

| 报告判断 | 当前证据 | 值得做的调整 |
| --- | --- | --- |
| 缺少社会认同 | 首页未见可核实用户评价、评分、媒体背书；商店实际评分本轮未核实 | 有真实材料再展示，写明来源、日期和授权；不要制造用户数或成功率 |
| 缺少创始人故事 | 首页没有明确的创作者介绍 | 增加简短的开发动机和联系人；个人经历需本人提供，不能编造 |
| 10 种语言没有突出宣传 | 已在首屏后的版本亮点中列出全部语言，并有功能卡片 | 先验证能否被看到；不要再堆一套语言模块。App 多语言不代表官网也已多语言 |
| 需要博客中心与作者署名 | 已有指南中心、8 篇文章、By Decrave、更新日期及来源 | 改进作者身份、资料核查方式和页面针对性；无需把 Guides 改名为 Blog |
| 没有软转化路径 | 已有 See how it works、指南中心和免费文章；缺少可互动的下载前体验与邮箱培育 | 先把现有指南入口用好，再决定是否做 SOS 体验；邮箱不是第一步 |
| 必须增加移动底部 CTA | 没有底部固定 CTA，但已有顶部 sticky 导航与下载按钮 | 实际测移动页面可达性；只有按钮仍难找到时才试底栏 |
| CTA 附近需回应费用、隐私和有效性 | 免费功能、同步和专业支持边界在定价/FAQ/页脚；首屏附近缺乏简短摘要 | 首屏突出免费核心功能、不需账号，并链接隐私说明；不承诺疗效 |
| 定价和年度优惠需完善 | 已有 Free、月付、年付、终身方案、美国区价格说明及 Save 58% | 对照 ASC 核实价格和试用资格；修正 CTA 的实际含义 |
| App Store 链接应进入具体页面 | 已带应用 ID 6801961627，以及 pt/ct/mt 活动参数 | 保留现有链接，验收目标页面和参数；不是从零接深链 |
| 网站关键词能加强 ASO | 官网 SEO 与商店搜索是不同系统；没有证据说明网页 metadata 直接提高商店排名 | 保持表达一致，分别看 GSC 和 ASC 数据 |
| 注册后马上转化为评分 | App 无自建账号；完成入门不等于已体验价值；下载链接不能“预填评分提示” | 以后在实际使用后的合适时机调用系统评分接口，保持自愿 |
| 需要紧迫感和稀缺性 | 报告自己也认为不适合本产品 | 保持真实、温和的语气，明确免费与可选付费即可 |

评分请求应在使用体验中的合适时机出现，不打断正在应对烟瘾的人，不提供奖励或保证好评。[Apple 评分与评价说明](https://developer.apple.com/app-store/ratings-and-reviews/)

### 技术、SEO 和追踪

| 报告判断 | 审查结果 | 优先级 |
| --- | --- | --- |
| 没看到 GTM/Hotjar/Segment，所以缺少分析 | 官网及指南已接 Plausible；App 有用户自愿开启的 TelemetryDeck；已有 Apple Website Campaign | 高：验收现有数据和建立口径，而非加工具 |
| 指南大概使用 WordPress/无头 CMS | 实际是静态 HTML，经 GitHub Pages 发布 | 不需要改 CMS |
| 需要 Article schema | 8 篇指南已有 Article；指南中心为 CollectionPage/ItemList；首页为 MobileApplication | 核查一致性，不重复搭建 |
| 需要面包屑结构化数据 | 页面有可见面包屑；抽查未见 BreadcrumbList JSON-LD | 中低：可小批次补齐，不能保证展示富结果 |
| FAQ schema 可获取富结果 | 已过时：Google 从 2026-05-07 起不再展示 FAQ 富结果 | 不为富结果专门新增 FAQPage |
| 健康内容需要 E-E-A-T | 方向成立；它不是一个可通过加署名直接获得的独立排名分数 | 高：真实身份、出处、准确性、纠错方式和更新记录 |
| LCP/INP 阈值 | 数值大体正确，但遗漏 CLS 和现场测量口径 | 先测量，再处理具体瓶颈 |
| 缺少 Android 是关键限制 | 是覆盖范围限制，但不自动构成当前增长瓶颈 | 后期需求验证，暂不迁移技术栈 |
| RN/Flutter 能低成本实现跨平台 | 没有针对本项目估算；SwiftUI、SwiftData、CloudKit、Widget、StoreKit 等需要重新设计或集成 | 不按“无需重写”假设决策 |
| PWA/Web App 是必需 | SEO 依赖可访问内容，不要求完整 Web App；PWA 也不能替代全部 iOS 原生能力 | 可先做单个网页体验，无需账号同步或完整 PWA |
| Health/可穿戴是 2026 必备 | 未证明对 Decrave 核心任务的价值；还增加数据与维护负担 | 暂缓，先验证明确使用场景 |
| 应接 Google Fit | 平台已进入迁移阶段，不能当作新项目默认选项 | 有 Android 需求时再按当时官方平台重新选型 |
| 网站没有隐私说明 | 已有隐私政策，描述 SwiftData、私有 iCloud、可选统计、第三方处理与用户选择 | 前置准确摘要，并核实实际配置 |
| 必须贴 GDPR/CCPA 与加密声明 | 有政策不等于完成合规；没贴标志也不能直接判定违法 | 依据实际地区、数据流和适用条件核查，不写未经验证的合规/加密保证 |
| 应加重定向像素、服务器追踪 | 当前没有流量及付费投放数据；与现有不广告追踪承诺存在冲突 | 当前不做。服务器端收集不会消除隐私约束 |
| B2B/API/webhook | 没有实际合作需求 | 后期有具体伙伴和数据需求再评估 |
| 版本 1.1 说明基础设施薄弱 | 版本号不能说明团队规模或技术质量；项目实际已有系统支付、存储、统计服务 | 不因为版本号重构基础设施 |

Google 明确说明 E-E-A-T 不是独立排名因子；健康相关内容尤其需要可靠性。作者署名的价值在于解释谁负责内容，不能虚构专家审阅。[Google 内容指南](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

Google 官方更新记录确认 FAQ 富结果已停止，6 月移除了相应文档。[Google 2026 更新记录](https://developers.google.com/search/updates#may-2026)

Core Web Vitals 的目标是 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1，按移动/桌面现场数据的第 75 百分位判断。实验室测试用于发现问题；无 CrUX 数据不等于性能不合格。当前截图合集约 876 KiB，仅凭体积不能判定它就是 LCP 瓶颈。[web.dev 指标说明](https://web.dev/articles/vitals)

Google 官方迁移文档说明 Fit API 支持到 2026 年底，并给出 Health Connect/Google Health API 等迁移路径。[Android 官方迁移指南](https://developer.android.com/health-and-fitness/health-connect/migration/fit)

## 3. 已有文案中优先修正的地方

1. **Most popular**：首页 Pro 卡片有此标签，未发现支持其含义的数据。建议删掉，或改成不依赖销量的事实标签。
2. **Start 7-day free trial**：按钮只打开通用 App Store 页面，无法直接开启试用。改成明确的下载入口，并说明符合资格的用户可在 App 内选择年付试用。最终措辞需先核实 ASC。
3. **对竞品的笼统结论**：首页声称多数 App 清零并使人放弃，没有调研依据。改为描述 streak 模式可能带来的压力，以及本产品实际保留哪些进展。
4. **免费与试用混淆**：核心免费功能无需订阅；Pro 试用是另一条路径。“无需信用卡”只可用于经验证的免费路径，不能暗示 Apple 订阅不存在支付要求。
5. **不清零的边界**：保留历史记录与累计次数，不等于吸烟不会影响健康，也不等于所有健康指标永不回退。
6. **练习中的烟瘾变化**：不保证计时结束后烟瘾消失，也不应说它“本来就不该消失”。强调练习的是应对方式，个人感受可能不同。

以上是准确性修正，即使小样本下无法测出转化变化也值得做。新增评价和创始人个人故事需要真实材料。

## 4. 目标、指标和观察方式

增长路径：搜索曝光 → 官网访问 → App Store 点击 → 商店产品页访问 → 首次下载。下载之后是否获得价值是质量检查，不能把点击或下载称为戒烟效果。

| 指标 | 来源与口径 | 用途与限制 |
| --- | --- | --- |
| 非品牌搜索曝光、点击 | GSC，按查询、落地页、国家、设备查看 | 自然搜索发现；品牌与非品牌分开，不凭总排名判断 |
| 官网访客 | Plausible，同一日期范围的 Visitors | 分移动/桌面与来源；iOS 转化优先看相关设备与市场 |
| 官网商店点击率 | 触发 App Store Click 的独立访客 ÷ 同范围独立访客 | 用访客口径，不能拿重复点击次数作分子；页面间不要把独立访客相加去重 |
| 各位置贡献 | 现有 button_location 属性 | 先看位置事件及点击访客；没有区块曝光事件时不能计算“看过按钮的人”的点击率 |
| 商店转化 | ASC 同一活动/日期范围的首次下载与产品页访问 | 核对后台统计定义；与网站不是同一用户队列，不当作精确贯通漏斗 |
| 获客下载量 | ASC Website Campaign 首次下载 | 指标有延迟和隐私门槛；缺失记为 unavailable，而非 0 |
| 初步使用质量 | 已有自愿统计中的 onboarding_completed、sos_opened、intervention_completed、day_n_active | 仅代表同意统计的人群；这轮不新增吸烟结果、诱因或强度上传 |

Apple 活动需要至少五位用户的首次下载才显示活动数据，各指标也有显示门槛，不能因空报表认定没有下载。活动归因有时间窗口，网站与商店报告不可能完全对齐。[Apple 活动链接说明](https://developer.apple.com/help/app-store-connect-analytics/acquisition/campaign-links)

每次观察记录发布日期、改动内容、流量来源、市场和版本。Product Hunt 上线、媒体提及等会改变访客组成，不能把总点击率变化全部归因于文案。

流量少时：先做可用性测试和事实纠错，数字只作为方向性观察。前后比较不是随机实验。以后有足够流量再根据基线转化率、希望检测的最小变化和可承受的周期计算 A/B 样本量；不按固定“跑一周”判胜，不凭两三次下载宣称显著提升。多项文案同时修正时只能评价整批表现，不能区分每一句的效果。

## 5. 分期执行计划

工作量是单人开发的初步估计，单位为工作日；观察期另外计算。第 1、2 期可以并行推进，避免等 SEO 的慢反馈再处理转化。

| 阶段 | 目标与交付 | 预计工作量 / 观察 | 通过条件 |
| --- | --- | --- | --- |
| 第 0 期：基线与通路 | 验收现有事件和 Website Campaign，建每周记录；核对 GSC 已收录/未收录原因；测移动首页与指南的加载和可达性 | 0.5–1 天；回看已有 7–14 天，若无历史则从现在记录 | 点击到正确商店页；事件位置可辨；缺失数据有说明；已知抓取问题有清单 |
| 第 1 期：首屏与信任 | 首屏明确免费核心功能、不需账号；隐私摘要及链接；指南软入口；修正 Pro CTA、Most popular 和过度竞品论断 | 拆成 2–3 批，共 1–2 天；观察 1–2 周或更长 | 目标用户理解定位与免费/付费边界；移动和键盘操作正常；事件与链接保留 |
| 第 2 期：现有 SEO 内容 | 先选 2 篇代表性指南改善查询匹配、署名责任、来源和内部链接；处理证据支持的索引/性能问题；有需要再补 BreadcrumbList | 2–3 天；观察 2–4 周起 | 可抓取、canonical 一致、数据与可见内容一致；对应查询曝光/点击有记录，不能保证排名 |
| 第 3 期：下载前体验或商店优化 | 根据瓶颈选择一个：轻量 SOS Web 体验；或商店截图/文案优化。移动底栏单独评估 | 2–4 天起；观察 2–3 周或更长 | 不牺牲原有直接下载路径；记录体验开始/完成与后续点击，或商店转化指标 |
| 第 4 期：有条件扩展 | 按已证实的国家/语言需求选择 1 个本地化落地页；评价、轻量分享、邮箱、合作等逐项验证 | 每个议题重新估算 | 有真实用户/渠道需求、维护能力和明确指标，再启动 |

### 第 0 期：先让数据可信

- 复用现有 Plausible、GSC、Bing、ASC，不装新分析产品。
- 验证首页 5 个按钮位置、指南页按钮事件，以及 pt/ct/mt 参数。使用测试标记/独立记录识别自己的验证点击，不把它们当增长。
- 记录首次下载与报表门槛，不尝试识别每个网站访客对应哪位 App 用户。
- 依据 10 月 1 日核查记录，在 10 月 4–8 日窗口复查指南抓取及索引；这是建议检查窗口，本计划未创建自动提醒。没有新错误不反复提交同一个 URL。
- 抽测首页和一篇指南的移动性能；有现场数据就看现场，缺少数据则记录实验室环境及结果。

### 第 1 期：拆成可以独立验收的小批次

**1A：首屏降低顾虑。**预计修改首页与样式 2 个文件，保留核心标题；下载按钮旁加入“Free SOS tools · No account required”等经核实的信息，增加简短隐私说明与链接。把现有指南作为可见的次级行动，测量 Guide Open（如确有必要）；不把阅读前强制交邮箱。

验收：在小屏 iPhone、桌面、放大文字及键盘操作下能找到下载、指南和隐私入口；App Store Click 保持原名称与位置。询问目标用户“是否必须先戒烟、什么免费、是否必须注册”，用误解而非喜好反馈改进。

**1B：定价与文案准确性。**核对实际商店商品后移除无依据的 Most popular，修正试用 CTA 和资格说明；在独立小批次调整竞品论断及练习预期。用用户输入补充创作者动机；资料未提供时先不写个人经历。

验收：月付、年付、终身切换后价格、周期、说明和 CTA 一致；美国区价格说明可见；免费路径与订阅试用不会混淆。

**1C：证据展示。**有真实评价、评分或媒体报道时再做。说明来源、商店地区、统计日期和展示授权，引用不夸大健康结果。尚未获得材料时跳过，不延误前两批。

### 第 2 期：先优化已有 8 篇指南

- 优先核查《无需先设戒烟日期》和《烟瘾袭来时怎么办》的收录、查询匹配与下载路径；如果数据提示其他页面更重要则调整顺序。
- 有真实查询时按查询改标题、摘要和回答顺序；没有查询时核对搜索意图，不宣称找到了“高流量关键词”。
- 已有 By Decrave 和来源列表；补充真实负责人或组织介绍、资料核查范围、纠错联系。只有实际专业人士审阅过才能标注专业审阅。
- 用具体下一步、操作示例和真实产品界面形成内容价值，减少泛泛健康科普与重复文章。
- 保留引用和支持资源；新增来源需核对原文，修改日期仅反映实际更新。
- 保持 Article、可见日期、作者和 canonical 一致；需要时补 BreadcrumbList。不为 FAQ 富结果新增结构化数据。
- 修复明确的抓取、重复规范网址或性能问题；图片压缩与拆分按测量结果决定。
- 不整站重做、不迁移 CMS、不一次翻译 10 种语言、不按周强制新增文章。

### 第 3 期：根据漏斗决定下一项

| 观察到的情况 | 下一步 |
| --- | --- |
| 有搜索曝光，点击很少 | 检查排名、搜索意图和标题摘要；低排名时不能只怪摘要 |
| 有官网访客，但商店点击少 | 先查设备是否适用、定位理解和顾虑；再试体验入口或移动 CTA |
| 商店点击不少，下载少 | 核实活动口径、地区可用性和商店页面；优先修截图与价值表达 |
| 下载后几乎没人完成核心操作 | 处理入门与 SOS 使用问题，避免继续扩大低质量流量 |
| 几乎没有访问 | 推进抓取与少量相关渠道资料，而非运行无样本的 A/B 测试 |

Web 体验只做一个短练习：无需账号、无强制邮箱、不存储个人烟瘾记录，允许随时结束，结束后说明可在 App 中继续。不保证烟瘾消失，也不把计时结束计为戒烟成功。先验证“是否更容易理解价值”，再看是否带来更多下载。

若需要移动底栏，先检查当前顶部下载按钮是否足够；底栏需支持 safe area、缩放、键盘和关闭方式，避免挡住内容。它是待验证方案，不预设必然提升。

## 6. 暂缓项目与启动条件

| 项目 | 何时值得重开 |
| --- | --- |
| 邮件工具包与培育 | 免费指南/体验已经有稳定使用，访客确实希望后续内容，且有持续运营能力；先明确订阅、退订、保存期限和实际数据流 |
| Android | 来自目标市场的有效 Android 需求反复出现，并能估算开发维护成本与获客价值；不能只看全球下载占比 |
| 官网多语言 | 某一国家/语言已有真实需求且相关商店可用；一次先做 1 种语言，正文/元数据/hreflang 一起验收 |
| 完整 PWA/Web App | 单个 Web 体验证实需求，用户需要持续跨设备使用；重新评估账号和同步成本 |
| HealthKit/健康平台/可穿戴 | 有与核心任务直接相关的使用场景，用户确认愿意授权，数据映射与平台能力可实现 |
| 奖励式推荐 | 真实自然分享已出现，且有留存和防滥用依据；奖励不可与好评绑定 |
| B2B2C/API/webhook | 有具体伙伴、明确工作流和付费意向；不能先建接口等待需求 |
| 广告像素/服务器端追踪 | 确定付费获客策略与预算，重新审查与当前隐私承诺的兼容性及适用要求；本阶段不接入 |

## 7. 每次更新的固定流程

1. 说明本批解决的一个问题、涉及文件和预期行为。
2. 小批次完成修改；超过 3 个文件时先展示具体方案，按项目协作习惯确认后再改。保持现有技术栈，新增依赖另行讨论。
3. 做相应验收：文案准确、链接/事件、移动布局、键盘可达性；不为纯文案改动扩建测试体系。
4. 提供可审阅结果与本批手动验证步骤。发布按当时明确授权执行；记录上线时间与可回退版本。
5. 按约定观察窗口复查；数据不足就写“尚不能判断”。事实纠错不因短期点击波动而恢复错误承诺。
6. 根据瓶颈决定下一批，不把整份清单一次性塞进产品。

### 首个实施批次的具体范围
